# 10-PROJECT-RULES.md # ZANEZION PROJECT RULES Version: 1.0 Purpose: This document defines the mandatory development rules for all developers and AI agents working on ZANEZION. These rules prevent: - Overwriting existing code - Duplicate APIs - Inconsistent database changes - Broken tenant isolation - Missing audit logs - Missing documentation updates - Untracked feature changes -------------------------------------------------- # GOLDEN RULE Before implementing any feature: 1. Read Overview.md 2. Read Business Requirements.md 3. Read Roles Permissions.md 4. Read Workflows.md 5. Read Database Schema.md 6. Read Prisma Rules.md 7. Read API Architecture.md 8. Read Backend Architecture.md No feature may be built without reviewing the Project Memory. -------------------------------------------------- # DO NOT OVERWRITE EXISTING CODE Never delete or replace working code unless explicitly requested. If a change is needed: - Extend existing modules - Add new functions - Add new routes - Add new validations Do not rewrite an entire file when only one endpoint changes. -------------------------------------------------- # FILE NAMING RULES JavaScript Files: user.routes.js user.controller.js user.service.js user.repository.js user.validation.js user.constants.js Folder Names: camelCase Examples: purchaseRequests guestRequests supportTickets -------------------------------------------------- # ROUTE RULES Routes only define endpoints and middleware. Never place business logic in routes. Correct: router.post( '/', authenticate(), validate(createOrderSchema), orderController.create ); Wrong: router.post('/', async (req, res) =&gt; { // Business logic here }); -------------------------------------------------- # CONTROLLER RULES Controllers may: - Read request data - Call services - Return responses Controllers must not: - Query Prisma directly - Implement business workflows - Implement approval logic -------------------------------------------------- # SERVICE RULES Services contain all business logic. Services must: - Enforce workflow rules - Validate status transitions - Trigger audit logs - Trigger notifications - Use transactions where required -------------------------------------------------- # REPOSITORY RULES Repositories contain only Prisma/database queries. Repositories must not: - Send notifications - Check permissions - Change workflows - Implement approval logic -------------------------------------------------- # PRISMA RULES Use Prisma ORM only. No direct MySQL queries unless performance critical and documented. Every schema change requires: 1. Update schema.prisma 2. Create migration 3. Update Database Schema document if structure changed -------------------------------------------------- # MIGRATION RULES Command: npx prisma migrate dev --name &lt;meaningful_name&gt; Examples: create_orders add_invoice_status create_guest_requests Never use: migration1 test newchanges -------------------------------------------------- # MULTI TENANT RULES Every business query must filter by tenantId. Example: where: { tenantId: req.user.tenantId } Never return data across tenants. Never trust tenantId from request body; use JWT tenantId. -------------------------------------------------- # RBAC RULES Every protected endpoint must use: authenticate() and checkPermission() Example: checkPermission('orders.create') Permissions are defined in Roles &amp; Permissions document. -------------------------------------------------- # VALIDATION RULES All POST/PUT/PATCH endpoints require validation. Use Zod schemas. Validate: - Body - Params - Query Never trust raw request input. -------------------------------------------------- # RESPONSE FORMAT RULES Success: { "success": true, "message": "...", "data": {} } Error: { "success": false, "message": "...", "errors": [] } Do not return inconsistent response shapes. -------------------------------------------------- # AUDIT LOG RULES The following actions must create audit logs: - Create - Update - Delete - Approve - Reject - Login - Logout - Export Audit entry must include: - userId - tenantId - module - action - recordId - oldValues - newValues - ipAddress - createdAt -------------------------------------------------- # NOTIFICATION RULES Trigger notifications for: - Order Created - Mission Assigned - Invoice Generated - Invoice Paid - Leave Approved - Payroll Processed - Support Ticket Assigned Store notifications in notifications table. -------------------------------------------------- # FILE UPLOAD RULES Store files in Cloudinary. Store only metadata in DB: - fileUrl - fileName - fileType - fileSize Never store binary files in MySQL. -------------------------------------------------- # TRANSACTION RULES Use Prisma transactions for multi-step operations: - Create Order + Items - Generate Invoice + Items - Inventory Transfer - Payroll Processing - Purchase Order Approval If any step fails, rollback everything. -------------------------------------------------- # SOFT DELETE RULES Business tables use deletedAt. DELETE endpoints should set deletedAt, not hard delete. Queries must exclude deleted records by default. Hard delete is allowed only for maintenance/admin tasks. -------------------------------------------------- # API VERSIONING RULES All APIs must live under: /api/v1 Breaking changes require a new version: /api/v2 -------------------------------------------------- # DOCUMENTATION UPDATE RULES Whenever a feature changes, update: - Development Progress - Database Schema (if DB changed) - API Architecture (if endpoint changed) - Workflows (if status flow changed) - Roles Permissions (if access changed) Never merge changes without updating memory docs. -------------------------------------------------- # DEVELOPMENT PROGRESS RULES After completing any task, append an entry to Development Progress: Date Module Change Summary Files Changed DB Migration Name API Endpoints Added/Changed Status -------------------------------------------------- # BUG TRACKER RULES For every bug: ID Severity Module Steps to Reproduce Expected Result Actual Result Root Cause Fix Commit / PR Status -------------------------------------------------- # TESTING RULES Every new endpoint should include: - Happy path test - Validation failure test - Unauthorized test - Forbidden test - Tenant isolation test Critical workflows should include integration tests. -------------------------------------------------- # SECURITY RULES Use bcrypt for passwords. Never log passwords or tokens. Use Helmet and CORS middleware. Apply rate limiting to: - Login - Forgot Password - Public endpoints -------------------------------------------------- # CODE STYLE RULES Use ES Modules. Use async/await. Prefer named exports for services/repositories. Avoid duplicate logic. Extract reusable helpers. Keep functions focused and small. -------------------------------------------------- # AI AGENT RULES AI agents must: - Read Project Memory first - Follow folder structure exactly - Avoid creating duplicate modules - Avoid changing unrelated files - Update memory docs after implementation - Ask for clarification if a business rule is missing AI agents must not: - Rewrite the entire project - Rename stable tables/models/routes without approval - Introduce new frameworks without approval - Disable tenant isolation or RBAC checks -------------------------------------------------- # DEFINITION OF DONE A feature is considered complete only when: - Route created - Controller created - Service created - Repository created - Validation added - RBAC applied - Tenant isolation applied - Audit logs added - Notifications added (if applicable) - Tests added - Swagger docs updated - Development Progress updated - Related memory docs updated If any of the above is missing, the feature is NOT DONE.
